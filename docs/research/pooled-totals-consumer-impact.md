# Consumer impact of pooled incentive totals (#153)

Planned model: a donation of amount `D` gives three separate pools of `D`: rewards, polls and goals. `PollOption.votes_cents` and `FundGoal.current_cents` increase by the allocation. The Channel/Event money total (`lib/donationTotals.ts`) increases by `D` only. So the sum of incentive amounts on one donation can be up to `3 x D`, and the sum over all incentives can be larger than money raised.

Source revisions read: esa-dono-ui `research/pooled-totals-consumer-impact` (= `origin/dev`), kollekt `4eb26ce`, esa-layouts-v2 `009487a`, esa-incentive-pipeline `7184096`.

## Answer

- No consumer validates, reconciles or asserts that incentive amounts sum to the donation amount or to the campaign total. Confirmed by reading the code paths below; nothing compares `target_contributions[].amount`, poll totals or target progress with `amount` or `total_amount_raised`.
- Every progress computation is **per incentive**: target `raised / amount`, poll option `raised / poll raised` (or `/ max option`). Pooling changes only the size of these numbers, not the arithmetic. Nothing breaks.
- Only one payload field carries a per-donation incentive amount: `target_contributions[].amount` in the Tiltify donation message (`tiltifyPayload.ts:86-89`). Under pooling it holds the goal allocation (`FundContribution.amount_cents`), at most `D`. `poll_votes[]` and `reward_claims[]` carry no amount; `amount`/`value_cents` stays `D`.
- Display risk only: kollekt shows the goal allocation next to the donation amount (`IngestionService.cs:171-177`). A reader can see "$10 donation, $10 to target X" and also a poll vote, which is correct but can look like double-counting. No code change is needed. A UI note or operator briefing is optional.
- Needed changes in this repo are tests and docs only: add a pooled contract test, and document that incentive totals are not money totals. esa-incentive-pipeline does not consume our data.

## Notes

- **Confirmed vs inference.** All "No" entries are confirmed by reading the cited code and by `rg` over each repo for the field names. "A reader may misread kollekt's allocation line" is inference about human perception, not a code fault.
- **Additive fields are safe.** If we later add `amount` to `poll_votes[]` or `reward_claims[]`, kollekt deserialises with default `System.Text.Json` options (no `UnmappedMemberHandling` setting found in `Kollekt.Rabbit` or `Kollekt.Shared`), which ignore unknown properties (inference from defaults), and layouts does not read these arrays. Do not change scalar fields to arrays (ADR-0009 `:30`).
- **Goal allocation per donation.** Under pooling the sum of `target_contributions[].amount` on one donation is at most `D`, because all goals share one pool. The 3x figure only appears if a consumer adds goal, poll and reward amounts together, and none does.
- **Server-side invariant to recheck (out of scope here).** `spend.ts` debits `Donor.balance_remaining` for every vote and contribution (`:101-111`, `:261-273`). Pooling needs three per-category balances or pool tracking instead; that is a design item for the server, not a consumer impact.
