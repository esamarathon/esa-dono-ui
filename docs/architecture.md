# Architecture

How the server, client and data model fit together. `AGENTS.md` keeps the invariants every change must respect and points here for the detail. Domain words are defined in `CONTEXT.md`.

npm workspaces monorepo: `server/` (Express + Prisma + SQLite), `client/` (React + Vite + Tailwind), and `packages/shared` (`@dono/shared`, cross-cutting TypeScript types). In dev, Vite proxies all `/api` requests to `localhost:3001` (`client/vite.config.ts`).

## Server

- `server/index.ts` — Express entry point. The Stripe webhook route **must** be mounted before `express.json()` because it needs the raw body buffer for HMAC verification.
- `server/lib/prisma.ts` — Prisma singleton using `globalThis` cache to survive hot reloads. For SQLite it forces `connection_limit=1` (concurrent interactive transactions otherwise deadlock) and a 15 s transaction `maxWait`. **Inside a transaction, always use the `tx` client**: a query on the global `prisma` from inside a transaction waits for that transaction and times out (ADR-0007).
- `server/services/stripe.ts` — Stripe SDK wrapper: `createCheckoutSession()` (hosted Checkout for a pledge), `verifyWebhook()` (signature verification via `stripe.webhooks.constructEvent`, or JSON parse when no secret), `isStripeConfigured()`, exact Session retrieve/expire and paginated lost-id discovery. Pledge creates use frozen parameters and the pledge token as the Stripe idempotency key. Degrades gracefully when `STRIPE_SECRET_KEY` is unset.
- `server/services/donation.ts` — Source-aware `intakeDonation()` for completed Stripe Checkout payments, wallet-only pledges and admin add (external donations and simulator). Owns donor resolution, money split, `total_donated`, Wallet credit, pledge resolution and fulfillment. Source adapters pass raw facts only. Intake records and publishes through `withWebhooks` in one transaction, then sends the magic link only after commit; rollback and duplicate external ids send no mail. `resolvePledge()` and `fulfillPledge()` are internal to intake. Auction settlement remains separate. Pooled intake records `amount_cents` as new money only, separate shipping, and zero initial Wallet credit. Wallet-only pooled pledges add $0 money and consume their existing hold once. Null-pledge/admin donations keep legacy Wallet credit; legacy email fallback is restricted to requests without a token and LEGACY pledges. A supplied unknown token never falls through to email. Exact-token old-shape late payments record new money/Wallet credit without D or allocations and link the original pledge with `LEGACY_PAID`. Pooled Stripe intake requires the exact bound Session id.
- `server/services/spend.ts` — Reusable `tx`-aware spend helpers shared between HTTP routes and intake. The optional final `PoolSpend` argument validates the source donation's category budget, live allocations, outstanding Pool credit and failed-refund gap without debiting Wallet credit. Claims record confirmed unit prices; votes/contributions split donor and auto provenance. Direct legacy spends still debit the Wallet.
- `server/services/pledge.ts` — `createPledge()` requires the pledge amount, draft id and client-shown plan. It validates live stock, prices, Channel, eligibility and text; rejects category overage (400), and returns corrected review (409) without a pledge/hold. Existing drafts return their immutable plan before comparison. Plan, prices/types and initial Wallet hold commit atomically. `createCheckoutForPledge()` uses confirmed new money, delegating Wallet-only fulfillment to intake. Creation persists its first attempt time and exact request before contacting Stripe; same-token retries cannot extend the deadline or use a pruned (>24h) idempotency key.
- `server/services/checkout.ts` — common reconciliation for return, cancellation, verified webhook notifications and admin Check Stripe. Only confirmed non-payment releases a hold. It preserves immutable review/funding during open, processing and unknown outcomes, and never overwrites fulfillment.
- `packages/shared/src/pledgePlan.ts` — exported pure `planPledge()`: independent Pool usage/overage, flat poll/goal proportional top-ups, integer largest-remainder/insertion-order ties, donor selection minimum, physical cash floor, Stripe 50-cent minimum, and shipping requirement. Client and server use the same function; stock, Channel eligibility and fallback remain server-owned.
- `server/services/email.ts` — Nodemailer magic link sender; donation intake calls it fire-and-forget after commit.
- `server/services/webhooks/` — outbound webhook messages (ADR-0007, runbook in `docs/outbound-events.md`). `outbox.ts` `withWebhooks(fn)` is the **only** way to emit: it runs the change and `emit(type, () => payload)` in one transaction (delivery rows + per-destination `seq` commit or roll back with the change) and wakes the dispatcher after commit. `delivery.ts` — `emitWebhookMessage(tx, …)`, payload builders, `signPayload()`. `dispatcher.ts` — strict per-destination FIFO drain: head = lowest-`seq` `PENDING` row with **no** time filter (not due → stall, never skip); endpoint failures (any transport error, any non-2xx incl. 4xx, missing RabbitMQ config) retry forever with 5/15/60/180 s backoff; message failures (empty/unparseable payload) → `FAILED`, queue moves on; in-process single-flight; 5 s safety tick; retention sweep deletes `SUCCESS` > 2 h and `FAILED` > 24 h, never `PENDING`. Admin requeue: `POST /api/admin/destinations/:id/deliveries/:deliveryId/requeue` and `/requeue-failed` (keep original `seq`). Prisma models `WebhookDestination`/`WebhookDestinationSeq`/`WebhookDelivery` map to tables `WebhookEndpoint`/`WebhookEndpointSeq`/`WebhookDelivery`; `message_type` maps to column `event_type`; `message_id` is one UUID per message (AMQP `messageId`). **Payload formats** (ADR-0009, runbook § Formats): a Destination is `NATIVE` (envelope, filtered by `event_types`) or `TILTIFY`. `TILTIFY` is RabbitMQ-only (400 on HTTP), and its routing key is carried per delivery (`WebhookDelivery.routing_key`). The `tiltify` exchange is asserted once per connection. `withWebhooks(async (tx, emit, publisher) => …)` supplies the donation publisher (`donationPublisher.ts`): `snapshot(ids)` before an existing donation changes, then `publish(ids, before)` after it changes (`null` for new intake). The publisher reads the donation and allocations inside the transaction and owns message and totals decisions; `forceForTransition(ids)` is reserved for transition corrections. It skips Tiltify builders when no `TILTIFY` Destination is active. Emit points: donation created/assigned → native `donation.created` + Tiltify donation + two totals. Any counted-money change → deduplicated Channel/Event totals, even when the status remains counted. Changed live allocations/status/money/pledge amount → opt-in native `donation.updated` (full safe replacement state) and a Tiltify donation under the same id only when its own content differs. Native creation includes allocation source; Tiltify never includes source or staff identity. Comparisons exclude generated message ids/timestamps; forced publication is transition-only. Moderator hide/show (`PATCH /api/moderator/donations/:id` `{ hidden_from_overlay }`) → `donation.hidden`/`unhidden` + a Tiltify donation (hidden = `"Anonymous"`, null comment, no `completed_at`). The `moderated` toggle → native only. `RewardClaim`/`PollVote`/`FundContribution.donation_id` link the rows to the donation whose pledge paid for them; the Tiltify donation lists those rows (not pledge items, which can fail), and a write-in vote only once its option is `ACTIVE`. Contract tests: `server/test/services/webhooks/tiltify.test.ts`.
- `server/middleware/adminAuth.ts` — Checks the `Authorization: Bearer key_admin_<key>` credential against `ADMIN_API_KEY` env var (ADR 0004).
- `server/middleware/donorAuth.ts` — Resolves the donor magic token from the `dono_session` httpOnly cookie (browser) or `Authorization: Bearer <token>` (API) to a `Donor` record; sets `req.donor`. The legacy `?token=` query param was removed.
- `server/lib/session.ts` — httpOnly `dono_session` cookie helpers (set/clear/read); the cookie value is the donor magic token, so revocation is unchanged.
- `server/lib/authHeader.ts` — Parses `Authorization: Bearer` into a typed credential (`donor_` / `key_admin_` / `key_mod_` prefixes; bare = donor token).
- `server/middleware/moderatorAuth.ts` — Grants moderator access via a `Bearer key_admin_`/`key_mod_` key match, or a donor (via `donorAuth`) whose effective `role` is `MODERATOR`/`ADMIN`.
- `server/lib/roles.ts` — Role constants (`USER`/`MODERATOR`/`ADMIN`), `hasModeratorAccess()`/`hasAdminAccess()`, and `resolveEffectiveRole()` which re-checks the `ADMIN_EMAILS`/`MODERATOR_EMAILS` allowlists on every authenticated request (never downgrading below the donor's persisted `role`).
- `server/routes/moderator.ts` — Moderator CRUD for polls, rewards, goals, claims, channels, and custom entry approval. Also exposes read access to **all donations** plus `PATCH /donations/:id` to toggle a `moderated` flag (`moderated_at`/`moderated_by`), so downstream tools (exports, leaderboards, future Discord role sync) can rely on which donations a human has reviewed. **Never selects/includes `donor.email`** in any handler — see the invariant comment at the top of the file and `server/test/routes/moderator-donor-email.test.ts`, which statically scans the whole file so a reintroduced leak fails CI regardless of which endpoint it's added to (this has regressed twice: fixed for claims/custom-entries, then again for donations, because the first fix wasn't swept file-wide and had no regression test). Only `server/routes/admin.ts` (gated by the admin key or an ADMIN session, `middleware/adminAuth.ts`) may expose donor email.
- `server/routes/channels.ts` — `GET /api/channels`, public list of active channels (used by the `/donate` channel picker). Channel CRUD lives in `admin.ts`/`moderator.ts` and delegates to `services/channels.ts` (see Events and Channels below).
- `server/routes/tiltify.ts` + `server/services/tiltifyApi.ts`: the Tiltify-compatible read API at `/api/tiltify` (ADR-0010, PRD-0002 §R). It replaces ESATiltifyBridge for kollekt and esa-layouts-v2. Routes: `campaigns/{id}` (a Channel with `team_id` = its Event, or an Event with `team_id: null`) and `campaign/{id}/rewards|targets|polls|polls/{poll_id}|milestones|matches`.
  - Responses are **bare** Tiltify-v5 objects and arrays; an unknown id returns 404.
  - Public; only the global API limit (`RATE_LIMIT_API`) applies.
  - Shared incentives (`channel_id = null`) are listed under every Channel; an Event lists none (kollekt#36 must look up incentives by id across campaigns).
  - Milestones and matches are `[]`.
  - `total_amount_raised` uses `channelTotalCents`/`eventTotalCents` from `lib/donationTotals.ts`, the same numbers as the `fact.updated` message.
  - Contract tests: `server/test/routes/tiltify.test.ts`. Consumer config: `docs/outbound-events.md` § Consumer setup.
- `server/routes/feedback.ts` — `POST /api/feedback`, public/unauthenticated multipart endpoint for the floating feedback widget (text + optional screenshot + session metadata). Gated on the `feedback` feature flag (404 when disabled) and rate-limited via `RATE_LIMIT_FEEDBACK`. Delegates to `server/services/feedback.ts`, which posts to the `DISCORD_FEEDBACK_WEBHOOK_URL` Discord webhook (503 if unset, 502 on Discord failure/non-2xx). Nothing is persisted — the server is a stateless proxy; metadata keys resembling `email`/`token` are stripped before forwarding.

## Moderator Setup

Donors have a `role` field (`USER` | `MODERATOR` | `ADMIN`, `ADMIN` implies moderator access). Roles are **never** granted as a side effect of donating — that would let anyone "buy" access with a self-supplied, unverified checkout email. Instead:

- Set `ADMIN_EMAILS`/`MODERATOR_EMAILS` env vars (comma-separated) to allowlist emails. `resolveEffectiveRole()` re-checks these allowlists on every authenticated request (in `donorAuth`), granting the role without ever persisting it as a result of a donation. Allowlist resolution is **gated on `Donor.email_verified`** — the email must have been verified via an OAuth login (Google/Discord) before it earns an allowlist role, so a self-supplied Stripe checkout email can never buy moderator/admin access. Donors not on an allowlist keep their persisted `role` (default `USER`), which an `ADMIN_API_KEY` holder can change explicitly via `PATCH /api/admin/donors/:id/role`.
- `MODERATOR_API_KEY`/`ADMIN_API_KEY` also grant moderator access directly via `Authorization: Bearer key_mod_<key>`/`Bearer key_admin_<key>` — an operational fallback independent of the donor/role system, useful for bootstrapping or scripting.
- Moderators/admins access their dashboard at `/moderate` via their magic link (the user menu, `client/src/components/UserMenu.tsx`, shows a "Moderate" link when `hasModeratorAccess(donor.role)`), or by entering a moderator key directly in the `/moderate` login gate. They can CRUD polls/rewards/goals, view claims (read-only — fulfillment status/toggle was removed from the moderator view, #56; only `/api/admin/*` retains a claim-status PATCH), and approve custom poll entries. They cannot access `/api/admin/*` routes (require the admin key).
- **SSO / verified identity**: `server/services/oauth.ts` + `server/routes/auth.ts` implement OAuth login for Google, Discord, and Twitch. `GET /api/auth/:provider` starts the flow (CSRF `state` in an HttpOnly cookie); the callback exchanges the code, upserts the donor by verified email (creating an empty donor on first sign-in), sets the `dono_session` httpOnly cookie, and redirects to `/wallet` (the token never appears in the URL). Google/Discord assert the email is verified (setting `Donor.email_verified = true`); Twitch has no verification flag, so its email stays unverified. A donor can also request a fresh magic link by email via `POST /api/auth/request-token` (rotates the token, uniform response to avoid enumeration).

## Webhook flow (`server/routes/webhook.ts`)

1. Signature verify via `stripe.webhooks.constructEvent(rawBody, req.headers['stripe-signature'], STRIPE_WEBHOOK_SECRET)`. Skipped if `STRIPE_WEBHOOK_SECRET` is unset (useful for local testing). Mounted at `/api/webhooks/stripe` with `express.raw` before `express.json()` so the raw body buffer is available.
2. `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_succeeded` and `checkout.session.async_payment_failed` go through common reconciliation. Only complete/paid enters intake. Complete/unpaid remains processing with its hold. Expiry is authoritative only for the exact bound Session. Verified async failure checks current Stripe state (including an expanded PaymentIntent): paid wins, open/unknown or an explicitly processing/retryable Intent retains funding, and confirmed failure releases once. Its `failed` receipt survives processing so a later Check Stripe can resolve it. Auction completed/expired handling stays separate.
3. Passes raw total, shipping, payment intent and pledge token to `intakeDonation({ source: 'stripe', … })`. Intake subtracts shipping from new money, extends the donor token TTL without rotating or granting roles, records the donation and fulfills/publishes inside one transaction. Pooled fulfillment grants zero Wallet credit; donations without a pledge credit their new money. Held funding stays bound to its authenticated donor, never to a self-supplied payment email. Comment/display name come from the confirmed pledge when present. Only after commit does mail go out; duplicate external ids/fulfilled pooled pledges and rollbacks send none.

## Pooled pledge core

The backend amount-first, checkout and reversal contracts are in place. The donate UI (#187) and remaining release slices must ship together. Do not deploy this intermediate integration branch.

1. **Review**: `planPledge({ pledge_amount_cents, selections, available_wallet_cents })` is pure. Each Pool equals D independently. Every donor selection is at least $1. Poll/goal remainders go proportionally to a single flat selection set, with exact integer largest remainders and insertion-order ties. Rewards have no automatic remainder allocation.
2. **Confirm**: `POST /api/pledge` requires D, `draft_id`, `plan`, `channel_id`, and `items` (which may be empty). Missing D or any `top_up_cents` fails with the reload message. Authentication is resolved before planning; email cannot authorize credit. A new attempt validates live prices, stock, Channel and text, repairs unavailable selections/reduced stock without raising D, and compares the same shared plan. Overages return 400; plan changes return 409 with `plan` and corrected `items`, creating neither pledge nor hold.
3. **Funding**: W = min(available Wallet credit, D − confirmed physical prices). If 0 < D − W < 50 cents, W = D − 50 cents. Initial hold debits available Wallet credit and increments held credit in the same transaction as the immutable POOLED pledge, confirmed plan and reward prices/types. Existing OPEN/fulfilled draft retries return the server plan with its original funding before any comparison.
4. **Checkout**: Uses confirmed `new_money_cents`, not a new Wallet estimate. Wallet-only fulfillment delegates to intake; physical rewards always need new money and shipping collection. One OPEN pledge per draft is enforced by the SQLite index. In-process creates coalesce; cross-process retries reuse the frozen request and token key. Stripe `expires_at` equals the immutable two-hour deadline, success returns to `/pledge/:token`, cancellation to `/pledge/:token?cancelled=1`, and `after_expiration.recovery` is explicitly disabled.
5. **Fulfillment**: Internal to intake. Pool spend mode does not debit Wallet credit again. Reward stock/type are rechecked, prices stay locked, physical claims cannot exceed confirmed new money. Poll/goal live failures release their allocations to remaining own choices proportionally. Pending write-ins participate; rejected options cannot receive votes. Goal money with no remaining choice follows the Channel's ordered list, then primary Channel's eligible list, then closest own goal before shared goals. Overshoot is allowed. No eligible goal, or no open poll choice, leaves reserved Unused pool money; polls have no default. Pooled fulfillment grants zero Wallet credit.
6. **Accounting/read compatibility**: Donation money and `Donor.total_donated` count new money only; shipping is separate and outside all Pools/totals. Claims/votes/contributions link to the source donation; poll/goal rows record donor/auto sources. Tiltify combines pooled provenance rows per option/goal while keeping the existing wire shape. New pledge responses contain `pledge_amount_cents`, funding and `plan`, never old totals. Read-only historical responses have `format: LEGACY`; null-pledge/admin donations retain legacy accounting.

## Checkout reconciliation boundary (#186)

- `GET /api/pledge/:token` reads the immutable review. `POST /api/pledge/:token/reconcile` checks Stripe without authenticating the donor. `POST .../cancel` expires first, retrieving after an unclear expire result; `POST .../continue` reconciles before returning the same payable Session. Cancel/continue require the owning session for a Wallet-bound pledge. `POST /api/admin/pledges/:id/check-stripe` is admin-only and runs the same reconciliation. There is no manual hold release or automatic sweep.
- Public `payment_state` is `READY`, `OPEN`, `PROCESSING`, `UNKNOWN`, `NON_PAYMENT`, `FULFILLED`, `LEGACY_PAID` or `PAYMENT_REVIEW`. `can_edit` is true only for pooled confirmed non-payment; `read_only`, `can_continue`, `donate_url`, `has_checkout` and `admin_review_required` support the donor/staff pages without exposing email, authentication tokens or shipping addresses. Cancel/continue/reconcile conflicts return 409 with `{error, pledge}`. Local expiry and sign-out do not establish non-payment. Returns never establish authentication.
- The serial migration `20261013000000_checkout_uncertainty` adds only `checkout_requested_at` and `checkout_request`. The intent and exact parameters commit **before** the external create. A null Session id after an attempted create is uncertain, not cancelled. Within 24 hours, recover by replaying the identical key/request; afterward, never replay that key. Paginated Stripe discovery must identify one original (not recovered) Session with matching token/reference/deadline before it can be bound and retrieved. No match or ambiguity stays blocked. Stripe calls are always outside database transactions.
- A normal late payment with funding still `HELD` fulfills the immutable plan even after local `CANCELLED`/`EXPIRED`. A payment that contradicts authoritative non-payment atomically reacquires **all** original W from available Wallet credit before normal fulfillment. If W is unavailable, the [approved amendment](https://github.com/esamarathon/esa-dono-ui/issues/186#issuecomment-6164165797) records actual cash once as a NULL-D donation and credits only that cash to Wallet credit, retaining routing/comment/name and linking the original pledge. Status `PAYMENT_REVIEW` flags admin review; no original incentive, debt, partial reacquisition or second credit is allowed. Literal example: D=1000, W=950, cash=50; if W was spent elsewhere, record only cash=50/NULL-D, not a 1000-cent fulfilled pledge. Shipping remains separate.
- Stripe documents that an expired Session cannot complete; complete/unpaid can still pay. The fallback above protects against contradictory provider notifications, not a supported same-expired-Session transition. Session identity matters: copied token metadata and recovery-created Sessions cannot consume the original hold. See [expire](https://docs.stripe.com/api/checkout/sessions/expire), [Session status](https://docs.stripe.com/api/checkout/sessions/object), and [indeterminate errors/idempotency retention](https://docs.stripe.com/error-low-level).
- Old OPEN legacy pledges are still expired by #184's pooled migration; terminal historical rows are unchanged. Exact-token late payment leaves raw `status=EXPIRED`, with derived `payment_state=LEGACY_PAID` from the linked cash-only receipt, without D or allocations. Original historical `FULFILLED` pledges stay fulfilled. A pre-transition lost create with no stored Session id can atomically bind its first verified paid, non-recovered Session only for this cash-only receipt; it never fulfills old incentives or uses held Wallet funding. A different Session cannot reuse that binding. Existing legacy async failure is received as `LegacyAsyncFailure` (`legacy_async_failure: {donation_id, checkout_session_id, pledge_token}`), with the bound pledge's `payment_status='failed'` persisted. The webhook consumes this receipt through the common legacy chargeback transaction and publisher before acknowledgement. Duplicate receipts and already-terminal historical donations do not apply a second adjustment. The remaining pooled release slices must still ship together.

## Physical Payment refunds (#191)

`services/paymentRefund.ts` owns the audited state machine and admin preview/list/read/retry/item/shipping APIs. It commits one `REQUESTED` record per source donation and claim `CANCELLING` before any external I/O. Stripe Session retrieval, durable PaymentIntent storage and refund creation run outside transactions. The record id is the idempotency key; metadata binds record, donation and claim. Retry exhaustively paginates PaymentIntent refunds and matches metadata before creating, even after 24 hours. Unknown outcomes retain locks. Definite creation rejection resolves `REJECTED` and restores `PENDING` without accounting.

Acceptance (`pending`, `requires_action`, `succeeded`) is **not final settlement**: it reverses only the selected physical claim/restores stock, lowers cash/D/`total_donated`, preserves Wallet funding and separately records last-physical-claim shipping. The second transaction commits accounting, the `pool_shrink_data` audit and common publisher outbox together, guarded by `accepted_at`. `paymentRefundShrink.ts` consumes Unused first, then applies exact largest-remainder reductions to live financial components and outstanding grants. Ended polls stay ended and completed goals stay complete, unlike ordinary goal reversals. Fully reduced poll/goal rows retire without credit; other reward entitlements are never canceled or multiplied. The serial migration `20261014000000_payment_refund_effective_funding` adds checked `PoolCreditRedemption.reduced_cents`; original consumption stays historical and only `amount_cents - reduced_cents` is restorable funding.

Signed `refund.*` notifications enter the same transaction boundary without changing Checkout/auction dispatch or raw-body verification. Identity, Stripe id, amount and PaymentIntent must match. Terminal state guards suppress duplicate/stale receipts. Accepted later failure/cancellation sets `FAILED`, with no automatic repair. Item resolution is outside return, Wallet credit only on COMPLETED/REFUNDED, or dispute settlement only on CHARGEBACK. Wallet recovery restores item money/D/`total_donated`, increments cumulative prior grants and the reserved failed-refund gap, and creates one uniquely linked `FAILED_PAYMENT_REFUND` adjustment. Allocations stay shrunk. Shipping has separate outside/kept-by-agreement audit fields and never becomes credit. The source Event's explicit end closes eligibility; Undo end reopens it. Full staff UI and operator rollout/runbook remain #193/#194; no live Stripe endpoint configuration is changed here.

## Balance mutations

`server/services/reversal.ts` owns every reversal in one transaction with the outbox. A nonnull donation pledge amount selects pooled accounting; NULL-D and unlinked rows keep the one-to-one legacy rule (ADR-0011 §§5–6). Pooled donor/auto item reversals create source-linked category Pool credit, moderator rows become computed Unused pool money, and neither writes Wallet adjustments. Claims always reverse at their recorded price. A Wallet refund returns the max-rule difference after prior Wallet grants, not the cross-category allocation sum; a chargeback returns original Wallet funding minus prior grants, with negative clawback capped at available Wallet credit. Both retain shipped claims; a chargeback flags them for explicit actor/time/note acknowledgement. `REQUESTED` Payment refunds block conflicting mutations; zero-money chargebacks and claim resurrection are blocked. Old terminal history is never repaired automatically. Only chargebacks block claim mark-pending/reverse: a retained shipped claim later reversed after a Wallet refund receives recorded reward Pool credit, not another Wallet grant.

The approved #188 goal policy recomputes completion against the target after reverse-spend, per-goal reversal and Wallet refund. A goal falling from $110 to $90 against a $100 target reopens. Chargebacks preserve completed goals. `poolAccounting.ts` exposes safe tx-aware current allocations, outstanding/spendable category credit and computed Unused pool money, with Event-end effects derived on read; no email, claim answers or staff identity are returned. Spend-budget validation shares this read interface. The admin reversal preview uses the same calculation as confirmation.

Direct legacy spends use `prisma.$transaction` with the `tx`-aware helpers in `server/services/spend.ts`, debiting available Wallet credit atomically with allocations. Pooled creation holds W atomically; intake consumes the hold without a second debit and calls the same helpers in pool mode. Pooled unused money is reserved, not Wallet credit. Database/outbox failures roll back donations, allocations, stock and hold consumption together.

## Events and Channels

Two levels, defined in `CONTEXT.md` (ADR-0008, PRD-0002 §S):

- **Event** (`Event`: `id`, `name`, `slug`, `is_active`, `primary_channel_id`) — the charity event: a marathon or a one-day stream event. Tiltify calls it a _team campaign_. An Event can only be active with an active **primary channel** of its own (`services/events.ts` `assertCanActivateEvent`); the primary channel of an active Event cannot be deactivated or moved to another Event (409).
- **Channel** (`Channel`: `id`, `name`, `slug`, `event_id`, `is_active`) — one stream within an Event. Tiltify calls it a _campaign_. Every Channel belongs to exactly one Event.
- **Slugs** (`lib/slugs.ts`) — `^[a-z0-9]+(-[a-z0-9]+)*$`, 3–64 chars, not reserved, unique across Events **and** Channels. They appear in URLs and AMQP routing keys (`<slug>.donation`), so a slug cannot change while its Event/Channel is active. No `.`: it is the AMQP topic separator.
- **Ids are UUIDs** (`@default(uuid())`) — kollekt requires them.
- Channel create/update/deactivate goes through `services/channels.ts` (shared by `/api/admin/channels` and `/api/moderator/channels`). `slug` defaults to one derived from `name`; `event_id` defaults to the only Event when exactly one exists (the migration creates `default-event`). `prisma db seed` makes one Event active with a primary Channel.
- **Default goal list**: existing Channel update accepts `default_goals: string[]` (ordered unique goal ids), restricted to own/shared goals. Inactive/completed entries are retained, not removed automatically. Public/staff Channel list and update responses expose the ordered ids. Lists start empty; live fallback is resolved only at intake.
- **Event API** (`services/events.ts`): `GET/POST /api/admin/events`, `PUT/DELETE /api/admin/events/:id` (delete = deactivate), mirrored under `/api/moderator/events`. New Events start inactive. The slug is fixed while active; the primary must be one of the Event's Channels; activating requires an active primary. Public: `GET /api/events` (active Events with their active Channels) and `GET /api/events/:slug` (`routes/events.ts`).
- **Donation routing** (`services/routing.ts` `resolveDonationRoute`, PRD-0002 §E5), applied in `intakeDonation()` for every source (wallet-only pledge, Stripe webhook, `simulate-donation`):
  1. a fulfilled pledge's Channel, or an explicit `channel_id` → that Channel and its Event;
  2. else `event_id` → that Event's primary Channel;
  3. else exactly one active Event → its primary Channel;
  4. else **unassigned** (`channel_id` and `event_id` null) and **no webhook message is queued**.

  An admin assigns it with `PATCH /api/admin/donations/:id/channel`, which sets both ids and publishes `donation.created` in the same transaction. A donation is never reassigned (409).

- **Donate URLs**: `/donate/<event-slug>` and `/donate/<event-slug>/<channel-slug>` preselect the Channel. `/donate` keeps its picker; `?channel=<id>` still works.
- **Every pledge routes to exactly one channel.** `POST /api/pledge` rejects missing `channel_id` with 400 and unknown/inactive Channels with 404. Intake copies the fulfilled pledge's `channel_id` onto the `Donation`; non-pledge donations (`POST /api/admin/simulate-donation`) may pass `channel_id` directly.
- **Incentives are channel-scoped or shared.** `Reward`, `Poll`, `FundGoal` and `Auction` have a nullable `channel_id`: `null` = shared (available from any channel); a set value scopes it to that Channel. `createPledge()` removes unavailable/foreign selections in its corrected review (409; no pledge or hold).
- `Donation.event_id` is set by routing (above). `hidden_from_overlay` is the moderator's Hide from overlay (see `server/services/webhooks/` above).
- **Per-channel totals are admin-only.** `GET /api/admin/stats` includes `channels: [...]`. The public `/api/campaign` keeps one overall total. **Money totals count `COMPLETED` and `REFUNDED` donations**. Wallet refunds keep the money. Payment refunds lower `amount_cents` in place while status stays `COMPLETED`; shipping stays outside totals. `CHARGEBACK` and `PENDING` do not count, and hidden donations do. One rule is shared by `/api/campaign`, `/api/admin/stats` and the cents metrics: `lib/donationTotals.ts` (PRD-0002 §E7).
- **Metrics** (`services/metrics.ts`, docs in `docs/webhooks-and-metrics.md`):
  - `dono_donations_unassigned` counts donations waiting to be assigned.
  - Per-Event/Channel breakdowns are **separate** gauges labelled `event`/`channel` (slugs, `""` when unassigned or shared): `dono_{donated_cents,donations,reward_claims,poll_votes}_by_channel`. They are separate so `sum()` never double-counts the unlabelled totals.
  - Only `dono_donated_cents_*` follows the money-total rule (`COMPLETED` + `REFUNDED` current `amount_cents`, shipping excluded). Incentive, Unused and Pool-credit cents are separate category measures, never additional money.
  - `services/accountingStats.ts` supplies one safe, tx-aware bulk snapshot to business gauges and admin/moderator stats. It reuses `computePoolAccounting`, sums effective reward funding components, and counts live entitlements once. Allocation labels follow the incentive; Unused/Pool-credit labels follow the donation. Event-end conversions are derived, not stored.
  - Admin stats expose current `pledged_cents`, available/held Wallet credit, open/overdue pledges, requested/failed refunds, per-Channel category amounts and shared incentive allocations. Moderator stats add comments-only/all Unused counts and category cents, without donor email.
  - Database gauges are interval-cached. Deduplicate replicas with `max without (instance)` **before** aggregating; never sum across incentive categories or mix them with money.
  - `dono_events_active` counts Events; `dono_channels_active` counts Channels.
- **Client**: `/donate` requires selecting a channel (`CartContext.selectChannel`) before showing incentives, pre-filtered to shared + that channel. Switching channels with channel-scoped items in the cart asks for confirmation (`pendingChannelId` / `confirmChannelSwitch`) and drops those items.

## Client

- `client/src/api/client.ts` — axios instance with `withCredentials: true`; donor auth rides the httpOnly `dono_session` cookie (no token attached in JS).
- `client/src/api/admin.ts` — separate axios instance that auto-attaches `Authorization: Bearer key_admin_<key>` from `localStorage.admin_key`.
- `client/src/api/moderator.ts` — axios instance (`withCredentials`) that sends the operational moderator key as `Authorization: Bearer key_mod_<key>` only when no donor session is active; otherwise relies on the session cookie.
- `client/src/pages/MyWallet.tsx` — determines login via `GET /api/donor` (cookie); a pasted `?token=` is exchanged for the session cookie via `POST /api/auth/session` and stripped from the URL.
- `client/src/pages/admin/AdminLayout.tsx` — renders a key-entry gate if `localStorage.admin_key` is absent; logout clears the key.

## Database

SQLite via Prisma. All monetary values are **integer cents**. `RewardClaim.claim_data` is a JSON string (SQLite has no native JSON column); routes must `JSON.parse`/`JSON.stringify` it. To migrate to Postgres, change `datasource.provider` and `DATABASE_URL`.

## OpenTelemetry / User Journey Tracing

Distributed tracing (user journey + backend) is wired into the sibling
[`esa-observability`](https://github.com/Codescales/esa-observability)
VictoriaMetrics stack via OTLP HTTP:

- **Browser** emits spans to `/traces` (same-origin), which nginx proxies to the
  `otelcol` gateway at `http://otelcol:4318/v1/traces`.
- **Backend** (`server/lib/tracing.ts`) emits OTLP HTTP directly to
  `OTEL_EXPORTER_OTLP_ENDPOINT`.
- W3C `traceparent` propagation links frontend and backend spans into a single
  distributed trace. The browser instruments axios/XHR (auto-injects the header),
  the server middleware (`tracingMiddleware` in `server/lib/tracing.ts`) continues it.
- `docker-compose.yml` does **not** join the `esa-observability_default` network by
  default (added complexity/dependency an admin opts into, not a hard requirement).
  To reach `otelcol` for tracing, an admin adds `networks: default: name:
esa-observability_default \n external: true` back to `docker-compose.yml` (or an
  override file) alongside enabling `OTEL_TRACES_ENABLED`/`VITE_OTEL_ENABLED`.
- Manual spans: `pledge.create`, `donation.process`, `pledge.fulfill` (server);
  `page_view`, `tab_visit`, `channel_select`, `cart_add`/`cart_remove`,
  `checkout_start`/`complete`/`error`, `pledge_return`, `wallet_view` (client).

The backend deliberately uses `NodeTracerProvider` + manual middleware rather
than `@opentelemetry/sdk-node` auto-instrumentations, because this app runs via
`tsx` and `import-in-the-middle` (used by auto-instrumentations) conflicts with
`tsx`'s ESM loader.

## Container images

Two production images (mirrors the esa-waypoint split backend/frontend pattern):

- **`Dockerfile.backend`** — Express + Prisma API. Multi-stage:
  - `test` target: full dev deps + source, entrypoint runs `scripts/run-tests.ts` (used by CI `container-test`).
  - `runtime` target: production API. Built from a slim `runtime-deps` stage (`npm ci --omit=dev`; `tsx` and `prisma` are production deps so no dev toolchain is shipped, and the base image's bundled npm is stripped). Applies `prisma migrate deploy` on startup via `docker-entrypoint.backend.sh`, runs non-root, SQLite lives in the `/data` volume (`DATABASE_URL=file:/data/dono.db`), health check on `/api/health`.
- **`Dockerfile.frontend`** — builds the Vite SPA and serves it via `nginx-unprivileged` on port 8080. `nginx.conf` (templated to `default.conf.template`) does SPA fallback and proxies `/api/` → `http://backend:3001`. Uses the built-in `15-local-resolvers` script (`NGINX_ENTRYPOINT_LOCAL_RESOLVERS=1`) so DNS resolution works on both Docker and Podman.

After building, always confirm the stack _functions_ — not just that the images build. `scripts/smoke-test.sh` boots the compose stack and asserts: backend health through the nginx proxy, SPA index + client-route fallback, admin-auth enforcement (401/200), an end-to-end donation simulation (proves migrations + DB writes), and volume persistence across a backend restart. It always tears the stack down on exit.

The CI `container-test` job runs `scripts/smoke-test.sh` against the freshly built runtime images, and `docker-publish.yml` runs it against the just-pushed `:<sha>` images (not `:latest`, so it verifies exactly what this run built, on any branch) after the Trivy gate.

Images publish to `ghcr.io/esamarathon/esa-dono-ui/{backend,frontend}` via
`.github/workflows/docker-publish.yml` (buildx multiarch amd64/arm64 + Trivy CRITICAL gate) on push to `main`/`dev` and on PRs against `main`. Every push tags `:<sha>` and a sanitized `:<branch>` (e.g. `:dev`); `main` additionally gets `:latest`. PRs publish `:pr-<number>` (Trivy-scanned, but skip the smoke test since there's nothing to compose/deploy). `docker-compose.yml` image tags default to `latest`, overridable via `BACKEND_IMAGE_TAG`/`FRONTEND_IMAGE_TAG` env vars to run a specific branch/commit build.
